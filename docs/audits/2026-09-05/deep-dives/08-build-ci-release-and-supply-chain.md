# Deep-dive 08: Build, CI, Release, and Supply Chain

## Scope and audit questions

- Is the release pipeline (tag → signed platform bundles → draft GitHub Release) reproducible and using secrets soundly?
- Is the dependency/license policy (`CLAUDE.md`'s permissive-only rule, with the documented `git2`/libgit2 exception) actually enforced, and does it currently pass against the real dependency tree?
- Are lockfiles and package-manager pins consistent across the JS packages in the audited tree?
- Is there a working, scheduled vulnerability-scanning job, and are workflow permissions minimal?
- Does the audited commit's CI/build surface accurately reflect what the repository (including its remote) actually ships, and is the working tree free of undocumented supply-chain risk (stray binaries, artifact provenance)?

## Paths examined

- `.github/workflows/ci.yml`, `.github/workflows/release.yml` (audited commit, i.e. local `main` @ `cd0cb63`)
- `.github/workflows/ci.yml`, `.github/workflows/release.yml` on `origin/main` (read-only, via `git show`/`git diff`, no checkout) — used only to characterize the divergence documented below, not as the object of this deep-dive's primary findings
- `docs/LICENSE_COMPLIANCE.md`, `scripts/check-license-compliance.py`
- `frontend/package.json`, `e2e/package.json` (`packageManager` field)
- `Cargo.toml` (workspace members), root `.gitignore`
- Untracked working-tree contents: `extension/artifacts/`, `extension/dist/`, `frontend/dist-vscode/`

## Evidence and checks run

- `python3 scripts/check-license-compliance.py` → exit 0, `"docs/LICENSE_COMPLIANCE.md covers every direct dependency."` This check only walks `crates/*/Cargo.toml`, `frontend/package.json`, and `e2e/package.json` (`scripts/check-license-compliance.py:24-31,66-77`) — at the audited commit there is no `extension/` or `crates/vscode-sidecar` for it to miss, so this is a true pass for the audited tree, not evidence either way about the extension's license posture.
- `grep -n packageManager frontend/package.json e2e/package.json` → both pin `pnpm@9.15.9`, consistent with `docs/ARCHITECTURE.md`'s note about a prior CI-vs-local pnpm-major mismatch (AUD-2026-09-05-CI-004 below covers a gap in this control).
- `git diff main origin/main -- Cargo.toml` → origin/main's workspace adds `crates/repo-service` and `crates/vscode-sidecar`; the audited commit's `Cargo.toml` has only `crates/git-core`, `crates/config`, `crates/tauri-app`.
- `git diff main origin/main -- .github/workflows/ci.yml` → origin/main adds an `extension` job (builds `vscode-sidecar`, runs the extension's own test/package/compile/lint scripts), adds `extension`/`e2e-vscode` to `build-dist`'s and a new `build-vsix`'s `needs:`, and adds the `build-vsix` job (per-target-triple sidecar + `.vsix` packaging, matrix over linux-x64/darwin-x64/darwin-arm64/win32-x64). None of this exists in the audited commit's `ci.yml`.
- `git diff main origin/main -- .github/workflows/release.yml` → origin/main adds `build-vsix-release` (stamps `extension/package.json`'s version from the release tag, builds a per-target sidecar + `.vsix`) and `publish-vsix-release` (downloads all `.vsix` artifacts, attaches them to the same draft GitHub Release `build-release` already creates via `softprops/action-gh-release@v2`). No separate marketplace-publish or Open VSX step; no additional secret beyond the implicit `GITHUB_TOKEN` for that release action, so this addition doesn't introduce a new credential-exposure surface by itself.
- `cat .gitignore` → covers `/target`, `frontend/node_modules`, `frontend/dist`, `e2e/node_modules`, `graft/`, `.claude/worktrees/`, `.worktrees/`; **no entry for `extension/` or `frontend/dist-vscode/`** at either the audited commit or (checked via `git show origin/main:.gitignore`) — origin/main does not add one either despite introducing both paths as real build-output locations.
- `git log --oneline main..origin/main` → `9bfd49e` "Ship Browsitory as a VSCode extension (Phase 6) (#66)" plus three follow-up fixes; `git log --oneline origin/main..main` → one commit, `cd0cb63` "docs(specs): add VSCode extension design spec (Phase 6)", whose own body still reads "Status: approved, not yet planned/implemented" even though the feature it describes had already shipped to `origin/main` two days earlier (`9bfd49e`, 2026-09-02) before this doc-only commit was authored locally.
- `git show origin/main:extension/package.json | grep version` → `"0.1.0"`. The untracked local artifact `extension/artifacts/browsitory-0.1.0-linux-x64.vsix` (6.9 MB) matches this exact default dev version, not any tagged release version (the only release tag in the repo is `release/0.2.0`, which predates Phase 6 entirely and is a desktop-only release). This is strong circumstantial evidence the `.vsix` and the sibling `extension/dist/*.js` / `frontend/dist-vscode/*` outputs were produced by a local, uncommitted, out-of-band build against extension source that is not present anywhere in the audited working tree or its reachable git history — most plausibly built from an `origin/main`-equivalent checkout, then left behind when the working tree was switched back to this stale local `main`.
- `du -sh extension` (from the parent session, corroborated here) → 1.3 GB, almost entirely `extension/e2e/.vscode-test/` (a downloaded VS Code test-host cache) and `extension/node_modules` / `extension/e2e/node_modules` — none of it reachable from any tracked path.

## Findings

### AUD-2026-09-05-CI-001 — Untracked, unverifiable `.vsix` binary and build outputs in the working tree

- **Severity:** High
- **Confidence:** High
- **Affected components:** Repository working tree / supply-chain provenance (`extension/artifacts/browsitory-0.1.0-linux-x64.vsix`, `extension/dist/*.js`, `frontend/dist-vscode/*`)
- **Evidence:** `git status --porcelain` shows all of `extension/` and `frontend/dist-vscode/` as untracked at the audited commit; no `.gitignore` rule covers either path; the `.vsix`'s embedded version (`0.1.0`, matching `extension/package.json`'s default on `origin/main`) does not correspond to any release tag, and the audited commit's own history contains no extension source at all to have produced it.
- **Impact:** A compiled VS Code extension package and a compiled webview bundle sit in the working tree with no commit, no CI provenance, and no way for a reviewer to confirm what source produced them or that they match any reviewed code. If a developer or script later ran `git add -A`/`git add .` from this working tree, this unreviewed binary would be committed straight to history. Because there's no `.gitignore` entry, nothing currently stops that.
- **Trigger / reproduction:** `git status --porcelain -uall | grep '^?? extension\|^?? frontend/dist-vscode'` from the audited commit; compare `extension/artifacts/browsitory-0.1.0-linux-x64.vsix`'s embedded version against `git tag -l` (only `release/0.2.0` exists) and against `git show origin/main:extension/package.json`'s version field.
- **Remediation:** Delete the stray artifacts from this working tree (they are safely reproducible from source and are not needed once the branch is brought current — see CI-002); add `.gitignore` entries for `extension/dist/`, `extension/artifacts/`, `extension/node_modules/`, `extension/e2e/node_modules/`, `extension/e2e/.vscode-test/`, `extension/e2e/out/`, and `frontend/dist-vscode/` so this class of artifact can't be accidentally staged in the future, mirroring the existing `frontend/dist` / `e2e/node_modules` entries.
- **Verification:** After remediation, `git status --porcelain -uall` from a from-scratch `extension` build (`pnpm install && pnpm compile && pnpm run package:vsix`) should show no untracked files outside intentionally-ignored build directories.

### AUD-2026-09-05-CI-002 — Audited commit is 4 commits behind `origin/main`, missing the entire VS Code extension surface

- **Severity:** High
- **Confidence:** High
- **Affected components:** Repository/branch state (local `main` vs. `origin/main`); every CI job that should cover `extension/`, `crates/vscode-sidecar`, and `crates/repo-service`
- **Evidence:** `git log --oneline main..origin/main` lists `9bfd49e` (Ship Browsitory as a VSCode extension, Phase 6, #66), `bb8a9eb`, `3318c44`, `3ebc59c`; `git diff --stat main origin/main` shows 105 files changed, +20765/-528, including all of `extension/src/*`, `crates/vscode-sidecar/*`, `crates/repo-service/*`, and the CI/release workflow additions cataloged above. The audited commit's own last local commit (`cd0cb63`) adds a design spec whose text says the feature is "approved, not yet planned/implemented" — factually stale relative to `origin/main`, which had already shipped and iterated on it (three follow-up fix commits after the initial merge).
- **Impact:** This audit's scope statement and every downstream deep-dive that touches the extension must treat it as **absent from the audited commit** — any finding about extension code correctness is necessarily sourced from `origin/main` via read-only `git show`, not from the tree actually being audited. More practically: whoever is working on this local `main` checkout has no access to Phase 6 in their own branch, risks re-doing work already merged upstream, and — combined with CI-001 — has stray binary build output from the very feature their branch doesn't contain.
- **Trigger / reproduction:** `git rev-list --left-right --count main...origin/main` (reports `1  4`); `git log --oneline main..origin/main`.
- **Remediation:** Fast-forward or rebase local `main` onto `origin/main` (a true fast-forward is likely possible here since local `main` has exactly one commit not on origin and no conflicting history — confirm with `git merge-base --is-ancestor main origin/main` after accounting for `cd0cb63`, or rebase `cd0cb63` onto `origin/main` if a strict fast-forward isn't available). Re-run this audit's scope-establishing step against the resulting HEAD before treating any extension-related finding elsewhere in this audit as final.
- **Verification:** `git log --oneline main..origin/main` returns empty after sync; `git status` shows no untracked `extension/`/`dist-vscode` artifacts once the corresponding source is actually checked out and `.gitignore` (CI-001's remediation) is in place.

### AUD-2026-09-05-CI-003 — `origin/main`'s license-compliance gate does not yet cover the extension's own dependency manifest in this diff

- **Severity:** Medium
- **Confidence:** Medium
- **Affected components:** `scripts/check-license-compliance.py`, `docs/LICENSE_COMPLIANCE.md`, `extension/package.json`
- **Evidence:** `scripts/check-license-compliance.py` changed by +32/-… lines between local `main` and `origin/main` (`git diff --stat main origin/main` shows `scripts/check-license-compliance.py | 32 +-`). This is consistent with the script being updated to also walk `extension/package.json`, but this deep-dive did not check out `origin/main` to confirm the updated script actually includes it (per this audit's "do not modify production code" / working-tree constraint, and to keep this finding's evidence within what was directly verified). What is confirmed: at the **audited commit**, the script has no knowledge of `extension/` at all (`WORKSPACE_CRATES`/`js_deps` calls only reference `frontend/package.json` and `e2e/package.json` — `scripts/check-license-compliance.py:24-31,66-77`), so a pass at this commit says nothing about the extension's dependencies (`webdriverio`-adjacent VS Code test tooling, any new npm packages `extension/package.json` pulls in) ever having been through the documented `cargo info`/`npm info` verification step.
- **Impact:** If the origin/main script update does not fully cover `extension/package.json` and `extension/pnpm-lock.yaml`'s direct dependencies, a non-permissive license could ship in the `.vsix` undetected. This is a coverage-gap risk, not a confirmed defect — confidence is Medium because the actual updated script content on `origin/main` was not read.
- **Trigger / reproduction:** Not applicable until the branch sync in CI-002 lands; then re-run `python3 scripts/check-license-compliance.py` against `origin/main`'s working tree and inspect whether it now enumerates `extension/package.json`'s dependencies.
- **Remediation:** After syncing to `origin/main` (CI-002), read the updated `scripts/check-license-compliance.py` and confirm it walks `extension/package.json`; if not, extend it the same way `frontend/`/`e2e/` are already covered, and add the corresponding table to `docs/LICENSE_COMPLIANCE.md`.
- **Verification:** `python3 scripts/check-license-compliance.py` passes against `origin/main`'s tree, and manually cross-check one or two `extension/package.json` entries (e.g. `@vscode/test-electron`, whatever CDP/webview-automation library `extension/e2e/src/support/webviewPage.ts` depends on) against `docs/LICENSE_COMPLIANCE.md`.

### AUD-2026-09-05-CI-004 — No CI verification that the `pnpm@9.15.9` `packageManager` pin is actually honored at install time

- **Severity:** Low
- **Confidence:** Medium
- **Affected components:** `.github/workflows/ci.yml` (`frontend`, `e2e`, and origin/main's `extension`/`build-vsix` jobs), `frontend/package.json`, `e2e/package.json`
- **Evidence:** `docs/ARCHITECTURE.md`'s testing-strategy section explicitly documents a past incident: "a CI-vs-local pnpm major-version mismatch broke `e2e/`'s frozen-lockfile install during Phase 1." The fix recorded is the `packageManager` pin in `frontend/package.json:6` and `e2e/package.json:5`, both `pnpm@9.15.9` — confirmed present and matching. However, `ci.yml`'s `pnpm/action-setup@v6` steps pin only the pnpm **major** version (`version: 9`), and there is no `corepack enable`/`packageManager`-aware install step verifying the exact `9.15.9` patch is what actually runs; a contributor's local Corepack-driven install (which does honor `packageManager` exactly) and CI's `pnpm/action-setup` (pinned only to major `9`) could still drift on minor/patch versions without either failing.
- **Impact:** Low-probability recurrence of the exact class of incident `docs/ARCHITECTURE.md` already documents once, now with a third `extension/pnpm-lock.yaml` in the mix on `origin/main` (which this deep-dive could not fully audit per CI-002) using `pnpm/action-setup@v6, version: 11` in origin/main's new jobs — i.e., origin/main's `extension`/`build-vsix` jobs pin pnpm **major 11**, different from `frontend`'s/`e2e`'s major 9, which is itself worth reconciling once the branch is synced.
- **Trigger / reproduction:** Not independently reproducible without a version drift actually occurring; this is a hardening/process-gap observation, not a confirmed failure.
- **Remediation:** Either have CI read `packageManager` from each `package.json` via `corepack enable` instead of hardcoding a version in the workflow, or accept the current major-only pin as sufficient and document why (e.g., if lockfile format compatibility across `9.x` patches is guaranteed). Separately, reconcile why `origin/main`'s extension-related jobs use pnpm major `11` while the desktop `frontend`/`e2e` jobs use major `9` — confirm this is deliberate (e.g., extension tooling requiring a newer pnpm) and not an unreviewed inconsistency.
- **Verification:** Add a CI step asserting the installed pnpm version matches the relevant `package.json`'s `packageManager` field; re-trigger CI and confirm it fails on an intentionally introduced mismatch, then passes normally.

## Coverage gaps, open questions, accepted risks

- **Not independently audited:** the actual content of `crates/vscode-sidecar`, `crates/repo-service`, and `extension/src/*` on `origin/main` — those are Phase 6 implementation correctness questions, out of this CI/supply-chain deep-dive's scope and properly the concern of deep-dive 06 (VS Code extension and transport bridge), which had the mandate to inspect that source directly via `git show`.
- **Not run:** `cargo audit` and `pnpm audit --prod` (the `audit` job's actual checks) were not executed in this session — running `cargo audit` requires network access to the RustSec advisory database, which may or may not be available in this environment; this deep-dive did not attempt it and cannot report a pass/fail. This is a gap: the audit's own severity table should not claim confidence about currently-known-CVE-free status without this having actually been run.
- **Not verified:** whether `TAURI_SIGNING_PRIVATE_KEY`/`_PASSWORD` and any VS Code Marketplace/Open VSX publishing secrets (none found in the reviewed workflow diffs — see CI notes above) are scoped with least privilege at the GitHub repository/organization settings level; that configuration lives outside the repository and wasn't accessible to this audit.
- **Accepted risk (documented, not a finding):** the `git2`/libgit2 GPL-2.0-with-linking-exception dependency is a deliberate, explicitly documented policy exception (`docs/LICENSE_COMPLIANCE.md`'s "The one exception" section) and is not re-litigated here.

## Strengths and positive controls

- The license-compliance gate (`scripts/check-license-compliance.py`) is real, automated, wired into CI's `audit` job, and currently passes against everything in its scope — not just aspirational documentation. The one intentional exception (`git2`/libgit2) is called out explicitly and its rationale is recorded rather than silently accepted.
- The release pipeline separates a fast, cheap `verify` sanity gate from the expensive multi-platform `build-release` matrix, and reuses the same `cargo test`/frontend test commands CI already runs on every PR — a tag can't skip the coverage a normal merge to `main` already required.
- Version stamping (`crates/tauri-app/tauri.conf.json`, and on `origin/main`, `extension/package.json`) is derived mechanically from the git tag at build time rather than requiring a manual pre-tag version-bump commit, removing a class of human error (tagging a commit whose manifest version doesn't match the tag).
- `origin/main`'s extension CI additions (not yet in the audited commit, but reviewed for this finding) follow the existing project pattern faithfully: a fast per-push smoke job (`extension`), a separate short-retention `build-vsix` validation job on `main`, and a release-time `build-vsix-release`/`publish-vsix-release` pair mirroring the desktop app's `build-release` structure — architecturally consistent, not a bolted-on afterthought.
- The `.vsix` release path attaches only to the existing draft GitHub Release (no separate marketplace auto-publish step, no additional secret surface introduced for that reviewed diff).
